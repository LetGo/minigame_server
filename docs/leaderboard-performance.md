# 排行榜隔离性能验证

## 范围与结论

## 当前门槛与历史压测适用范围

当前源码及正式门槛为 stage≥101、boss≥30，测试仍500/50，见 [leaderboards-api.md](leaderboards-api.md)。以下500/50全规模压测不能充当当前101/30版本的实测。300/30历史中间版本于2026-10-19发布，通过118项集成、40玩家/200操作真实HTTP smoke（错误0），但未重跑全规模；本文也没有101/30版本的新全规模压测证据。

历史服务端门槛：stage≥500、boss≥50。证据`tmp/leaderboards/thresholds/benchmark-results.json`，Node24.16.0；候选产物及脚本哈希在当次交付时回读匹配。**当轮造数全部达到门槛**：各档是真实1万/10万/100万入榜玩家，并未通过过滤掉多数玩家来降低测试负载。另有真实集成测试覆盖未达标保存、零分、临界值、达标入榜、后台补投影、丢索引重建及旧无门槛缓存替换。

以下表格与资源观测为**增加入榜门槛之前的历史测试**，只作历史对照，不覆盖上述最新结果；原始历史JSON未覆盖。

这是本机一次合成、闭环压测，不是生产容量承诺，也不是微信真实玩家联调。真实执行候选编译产物的鉴权、HTTP路由、Redis排名、PostgreSQL最高值持久化及资料批量查询；没有伪造接口或替换数据存储。

累计三档每榜人数：10,000、100,000、1,000,000。完整原始证据：`tmp/leaderboards/benchmark-results.json`，摘要 `benchmark-summary.json`，资源观测 `benchmark-resources.json`。每档包含排序/同分/自身榜外/最高值/分榜隔离/持久化断言。百万榜仍只读取前30和本人，不全量排序。

## 条件

- Node.js 24，本机 loopback HTTP；Node进程未单独CPU/内存限额，与现有服务共享主机。
- PostgreSQL18、独立15442端口、测试专用数据库与凭据；tmpfs；容器CPU上限1核、768MiB。shared_buffers32MiB、max_wal_size64MiB，测试库连接禁用JIT。
- Redis8、独立16392端口；CPU上限1核、384MiB；maxmemory256MiB、noeviction；关闭持久化。
- **生产PostgreSQL是持久磁盘、Redis有AOF，因此本结果尤其不能直接推断生产写入容量。**不含公网、TLS、Nginx、微信换码耗时，不包含榜单重建/造数时间。
- 分数按SQL确定性生成，同分使用规范UUID字典序降序；资料仅为前30及本人创建，其他用户走缺省资料。不是百万份头像资料冷热缓存压力测试。
- 每档每种负载各测顺序并发1与闭环并发20、每组1,000次。Redis单项负载为更新/本人排名/前30；HTTP负载为完整榜单查询及真正提升最高值的上报。各用户跨操作请求不突破实际60次/分钟规则，不修改限流配置。
- 这里是分别测查询和上报，不是20并发查询再叠加20并发上报的混合负载，也不是寻找最大饱和QPS或持续长稳容量。

## 恢复及内存

| 每榜人数 | SQL造数 | Redis缺失后的真实重建（含首次查询） |
|---:|---:|---:|
| 10,000 | 0.270s | 0.053s |
| 100,000 | 2.764s | 0.276s |
| 1,000,000 | 27.883s | 2.914s |

恢复是故障路径，不算稳态延迟。当前恢复期间同榜的成绩提交被排他advisory锁保护，其他实例可能返回503 `LEADERBOARD_REBUILDING`；服务端每条SQL/Redis操作有限超时，重建总预算60秒。客户端不能把恢复503显示成空榜。

Redis `MEMORY USAGE` 是键内存的采样估算，不是进程RSS。观测容器整个生命周期峰值：PostgreSQL616.29MiB、Redis108.84MiB，均无OOM/被杀；峰值涵盖本次三档完整压测和造数/清理，并非某一阶段单独值。数据库体积包括用户/成绩及索引等，不能误当成单纯排名索引大小，且不包括WAL。

### 正式环境的容量边界（历史检查与后续授权扩容）

历史压测时正式Redis为maxmemory96MiB、容器192MiB/0.5核，单榜估算已超该旧上限。此后用户另行授权在线增容并重建，2026-10-19正式Redis已为maxmemory512MiB、容器1536MiB/1核，保留AOF/noeviction，见`redis-online-expansion.md`。本压测仍是maxmemory256MiB且无AOF的隔离环境，**不是最新正式Redis同配压测**；不能据此承诺生产百万榜容量。门槛减少的是实际入榜人数；所有玩家都达标时不节省对应成员内存，固定门槛也不是人数硬上限。

**按百万级两张榜部署前必须重新规划Redis内存**，为会话、两张榜、分配器及临时重建留余量；不能把单榜112.33MiB直接当成整个服务内存需求。数据规模上来应分离排行榜Redis实例，而不是只换DB编号。

查询探针验证：每次资料查询1次、最多31个UID，未观察到全榜排名SQL。主路径复杂度为：上报Redis索引O(log N)，本人名次O(log N)，前30 O(log N+30)；数据库更新仍有事务/WAL成本。

## 可重复执行

只允许独立测试端点，脚本启动前硬校验；不读取`.env`，拒绝生产15440/16390、持久测试15441/16391、普通集成测试15439/16389或公网地址。默认无参数不执行压测；同一时间只运行一个实例。

```bash
sudo docker compose -p minigame-leaderboard-benchmark -f compose.leaderboard-benchmark.yaml up -d --wait
npx tsc -p tsconfig.build.json --outDir tmp/leaderboards/benchmark-dist
node scripts/benchmark-leaderboards.mjs --validate-only
LEADERBOARD_BENCHMARK_TEST_REAL=1 node --test test/leaderboard-benchmark-ops.test.mjs
node scripts/benchmark-leaderboards.mjs --run
sudo docker compose -p minigame-leaderboard-benchmark -f compose.leaderboard-benchmark.yaml down
```

脚本每档完成原子写JSON，最终清理并回读验证用户0、Redis键0；非完整运行看 `complete:false` 及失败phase，不能引用为完成结果。脚本造数/清理只操作上述一次性端点，绝不能修改端口映射指向持久环境。

后续上线前还需要真实客户端调用、按实际活跃人数/请求频率的混合长稳压测，以及生产内存/持久化配置评估。本轮不更改正式服或常驻测试服。
