## 与首次来源的区别

- 既有 `game_users.source_scene` / `source_scene_reported_at` 仍是首次注册来源，不覆盖、不推测补填老用户，原 `/users/source-scene` 行为不变。
- 新增 `game_login_events` 保存每一次成功登录的用户、应用、数据库登录时间与本次请求的 `scene`。同一用户同一天重复登录也分别记录；省略 `scene` 则保存 NULL，不拿首次来源或上一条登录值代替。
- 客户端继续使用现有 `POST /auth/wechat-login` 的可选 `scene` 字段，无需新增接口或二次上报。取值校验保持 JSON 整数 1..2147483647；它是客户端报告，不是微信平台核验的归因证明。
- 登录成功以登录数据库事务提交为准：事件、用户状态及当天去重活跃在同一事务提交。会话创建失败或数据库事务失败不得留下已提交的事件；事务已提交但 HTTP 响应丢失，仍可能留下一次登录记录，不承诺客户端实际收到了 token。
- 新记录不是在线时长、IP 审计、客户端版本快照，也不改变 DAU / 次留：这些仍读取 `game_daily_logins`，每用户每北京日一条。

## 看板

- 登录日志新增 **本次登录场景**，接口字段 `items[].loginScene`；原 **首次来源场景** / `sourceScene` 保留。
- 新采集的数据逐次展示，保留查询日期、北京时间、50 条分页、当前昵称及最近成功上报版本等既有语义。客户端版本仍不是逐次快照。
- 原 `game_daily_logins` 的历史首次成功登录记录继续展示，但本次场景显示 `—`。新事件与逐日表在同用户、同应用、完全相同登录时间对应的一条记录只显示一次。
- 历史只保存了每天第一次登录，不能还原采集上线前每次登录或当时的 scene；不进行历史回填、不伪造事件。日志条数不等于 DAU，翻页期间新登录仍可能推动 OFFSET 页边界。
- 本次场景与首次来源使用同一已有的微信场景描述映射；2026-11-01已更新为单元格显示原始场景ID、title保留完整描述，未知值仍保留，详见 [dashboard.md](dashboard.md)。

## 部署前提（本文件不构成部署授权）

1. 先完成独立测试和审查，再取得目标环境部署授权。正式服、持久测试服分别授权，不能因开发请求而直接重启线上。
2. 用目标数据库 owner 应用新增 `013_login_events.sql`；不要用受限 API 角色自动迁移，不改既有迁移文件。
3. 目标 API 角色仅需新增事件表 **INSERT** 权限；看板角色仅需 **SELECT**。主键为 `GENERATED ALWAYS AS IDENTITY`，插入路径不读取事件、不返回主键，不要求 API 角色拥有该表 SELECT 或身份序列权限；受限角色测试验证这一边界。不授所有表、UPDATE、DELETE、DDL 或超级用户权限。
4. 迁移及权限就绪后再切换包含新写入逻辑的 API 构建，随后切换新看板。看板若先发布到尚无事件表的库，登录日志将查询失败；API 未获事件插入权限时会拒绝登录并回滚，不能漏记后照常发 token。
5. 数据库迁移为空新表，不复制历史逐日记录。保留既有逐日表及其统计用途。
6. 回滚只恢复 API / 看板构建并重启经授权的对应服务，保留新增表与已采集真实事件；不删表、不清历史、不自动删玩家。

在明确授权目标环境发布后，由对应数据库 owner 执行的新增最小权限 SQL（不是运行时自动执行）：

该表按登录次数增长，目前没有自动清理、归档或分区策略；本次未擅自设置保留期限或删除历史。发布时应评估每日登录量、磁盘与查询耗时；大流量下另行确认归档/分区方案，不能以本机测试替代容量保证。
